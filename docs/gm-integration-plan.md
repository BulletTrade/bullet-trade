# 掘金数据与交易完整接入计划

日期：2026-10-04。状态：原始接入方案。2026-10-08 已完成本地 Broker 候选版及银华日利仿真往返，见[实施与验收](gm-trading.md)；后续章节保留原计划口径，远程服务尚未交付。

## 接入目标与当前基础

把掘金作为 BulletTrade 的正式数据和交易后端，沿用现有策略 API、LiveEngine、Broker 注册和 Server adapter。策略使用标准的数据查询、下单、撤单及账户接口；掘金的代码、会话和回报差异由适配层处理。

运行数据仅来自掘金。聚宽 RPC 只用于独立的开发验收，不进入 Provider、交易 worker 或运行配置，也不作为缺字段时的自动后备源。

| 范围 | 当前证据 | 接入判断 |
| --- | --- | --- |
| 独立 GM 数据 Provider | 已采集样本的实用验收 52 通过、0 失败 | 可作为首版基础；覆盖范围见数据适配文档 |
| 相关离线回归 | 612 通过、0 失败；5 项旧联网用例未执行 | 保留为后续回归基线；其中 42 项为新增验收规则测试 |
| 严格数值诊断 | 32 通过、20 项差异 | 原始差异保留；按已确认的容差和后复权同日基准归一化验收 |
| 账户只读查询 | 候选账户已连接，资金、空持仓、空委托、空成交可查询 | 尚需确认 SDK 账户 ID 与终端仿真账户的身份对应关系 |
| 下单、撤单、成交及重连 | 未完成交易验收 | 是下一阶段的主要工作 |
| Broker / Server / 完整策略链路 | 未实现 GM 交易接入 | 需要按以下阶段补齐 |

52 项数据验收不代表全证券、全历史或所有 API 均可用。Finance 分红事件表的基准调用仍有远端线程故障，盘中新鲜行情和部分增值权限未验收；使用这些能力的策略需另行核查。数据比较容差只用于跨源验收，不用于修改成交价、成交量或资金账目。

## 运行架构

### Windows 本地执行

```text
自己的策略
  -> BulletTrade 标准数据 API / LiveEngine 交易 API
       -> GmDataProvider -> 隔离的数据 worker
       -> GmBroker       -> 常驻的交易 worker
                             -> gm.api SDK -> 掘金终端 -> 行情 / 交易账户
```

交易 worker 管理 SDK 实时入口、事件循环、账户绑定和回报，不负责策略选股、择时或仓位决策。自己的策略仍由 BulletTrade 运行。外部 SDK 接入是优先方案，不要求复制大 QMT 的终端内 HTTP helper。

现有数据查询采用有超时的短时独立进程；交易必须使用持续接收回报的会话。此前已观察到原生 SDK 退出会影响进程，因此默认把 SDK 与策略进程隔离。第一阶段先验证两个 worker 的会话是否能共存、策略身份是否会相互替换；若不能共存，就由隔离的常驻 SDK worker 同时承接白名单数据查询与交易，两个标准接口保持独立。不要在验证之前假定相同策略 ID 可被多个进程同时使用。

优先使用已安装、已经读通的 `gm.api`。`gmtrade` 公开提供另一套交易 API，但不能直接认定其与当前华鑫终端版本、账户和权限兼容；首版不自动增加该依赖。如果 `gm.api` 的实机合同确实不足，再根据兼容性证据调整 SDK 选择。

### 远程执行

```text
Mac / Linux / 另一台 Windows 上的策略
  -> BulletTrade 远程数据与交易客户端
  -> 现有 BulletTrade Server（JSON/TCP、鉴权、TLS、账户路由）
  -> GM 数据 / 交易 adapter
  -> 同一套 Provider、GmBroker 与隔离 SDK worker
  -> Windows 上的掘金终端
```

增加 `--server-type gm`，复用现有协议、请求幂等和写入边界机制。现有远程客户端仍有 QMT 命名和环境变量耦合，应抽取必要的公共配置入口，再以 `gm-remote` 和对应数据源入口包装。保留 QMT 旧名称和配置兼容；避免复制一份下单、撤单、超时处理代码形成两个实现。

本地与远程执行是两种部署方式，不意味着同一策略同时由两个执行器写同一账户。首版明确每个账户的交易写入所有者。

## 首版功能范围

首版闭环以 A 股普通股票和 ETF、日线/分钟定时策略、明确账户、限价买卖为目标。已有历史数据能力继续保留，补齐策略运行必需的最新报价、账户查询、订单及成交同步。市价单按交易所及柜台支持情况另行开放，未支持时明确报错，不能悄悄转成限价。

| 标准能力 | GM 接入内容 | 关键合同 |
| --- | --- | --- |
| 数据与元信息 | 复用 `GmDataProvider`，验证运行时引用日期、时间边界和报价新鲜度 | 数据独立；过期行情显式标记/拒绝，不能冒充当前报价 |
| 资金 | `get_account_info` | 总资产、现金余额、可用现金、冻结资金分别映射；缺字段不能填零冒充真实查询 |
| 持仓 | `get_positions` | 总持仓、成本、市值、当日买入和实际可卖数量；区分股票 T+1 与适用品种的其他规则 |
| 限价交易 | `buy` / `sell` | 证券代码、股数、价格最小跳动、买卖方向和账户显式映射；不自动扩大订单数量 |
| 撤单 | `cancel_order` | 只撤指定账户的指定原委托；发出撤单请求不等于已经撤成 |
| 委托 | `get_orders` / `get_open_orders` / `get_order_status` | 新建、已报、部分成交、已成、已撤、部撤、拒绝等状态及原生身份保留 |
| 成交 | `get_trades` 与回报 | 只计实际成交；累计成交快照不作为新增成交重复入账 |
| 运行生命周期 | `connect` / `disconnect` / `heartbeat` / `cleanup` / 同步 | SDK 与账户均就绪才连接成功；断线暂停写入，恢复先对账 |
| 远程服务 | `RemoteDataAdapter` / `RemoteBrokerAdapter` | 同样的标准 DTO、账户隔离、幂等与不确定提交语义 |

财务、行业/概念、基金净值、信用交易、期货/期权、算法母单、虚拟子账户分配和 tick 高频订阅作为后续能力，单独列出支持矩阵。基础普通交易不能依赖 TWAP/POV 等权限。标准 API 已有但 GM 暂无实现的能力必须明确报不支持。

## 交易正确性设计

1. **账户身份**：所有查询和写入显式传账户 ID。配置的策略 ID、token、资金账户 ID 分开处理。终端显示已连接只是证据之一，还要核对 SDK 实际账户身份、类型和更新时间。首版一次绑定一个明确账户，服务端保留账户路由扩展点。
2. **委托身份**：记录本地请求 ID、幂等键、账户 ID、`cl_ord_id`，以及 SDK 返回的 `order_id` / `ex_ord_id`。账户与原生委托身份共同定位订单，不能仅凭代码、时间和数量猜测是哪一单。
3. **成交去重**：以实际可验证的成交身份去重；必须检查当前终端是否提供稳定 `exec_id`。缺少可靠身份时，验证可用的替代证据和查询重建方式；证据不足不能把两条同价同量回报直接合并或重复记账。
4. **提交与成交分开**：SDK 返回委托表示某个提交阶段；最终状态和实际成交由回报及查询确认。部分成交、撤单拒绝、委托拒绝分别保留原因。
5. **不确定提交**：写前持久化请求身份与载荷指纹，记录准备、发送、已接受、明确拒绝、结果未知。发送边界后的异常或超时进入 `submit_unknown` / 对账，不自动重发。重启后查询原委托；查不到一次不是“确定没下过单”。若 SDK 不能预设客户端身份且崩溃导致关联丢失，必须保持未知并冻结该请求的自动重试，不能推测失败。
6. **写入边界**：远程复用 `BrokerCallBoundaryMarker`。跨进程转交不能把内存回调直接序列化，应先持久化并与 worker 确认交接；凡无法证明 SDK 尚未写入的状态均按可能已提交处理，允许保守地保持未知。
7. **恢复及账户一致性**：断线重连获取账户、委托和成交完整快照，再恢复写入；核查回报乱序、重复及迟到处理。保留未决请求的资金/持仓占用，审查 LiveEngine 是否会把未知结果误标失败或释放预留，必要时做最小的共享接口修正。
8. **资金、数量账目**：成交数量精确核对，资金按币种精度和实际手续费对账；股票持仓增减、冻结/解冻、余额与市值分别核对。同一观测时点或可解释时间窗口内比较，不把正常异步更新时间差误认为账错。

交易日志不保存 token、密码或完整敏感配置；记录账户脱敏标识、状态转换、版本和证据时间。请求日志、订单关系及成交去重信息必须能跨 worker / Server 重启恢复，不能只依赖现有 Server 的内存幂等缓存。

## 实施阶段与验收条件

| 阶段 | 交付内容 | 完成条件 |
| --- | --- | --- |
| P0：冻结合同与开发基线 | 对齐当前克隆与主工作区开发版本；SDK 函数、事件入口、账户 ID、版本与能力探针 | 明确实际 SDK 合同、账户身份、查询范围、会话共存和回报身份；文档事实与本机实际版本分开记录 |
| P1：本地账户后端 | 常驻交易 worker、IPC 客户端、DTO 映射、`GmBroker`、注册与配置；先只读 | 标准账户/持仓/委托/成交接口读通，错账户和空/失败查询可区分；导入或构造后端不会启动 SDK/连接账户 |
| P2：本地交易与恢复 | 限价买卖、定向撤单、状态机、请求日志、去重、重连；接入 LiveEngine | fake SDK 故障矩阵通过；策略订单与券商事实同步；未知结果不重发、不会漏记/重复记成交 |
| P3：仿真真实闭环 | 交易日的指定仿真账户测试及一条标准 API 策略 | 买入受理/成交、部分成交或等价回报重放、拒单、撤单、账户更新及重启恢复有完整证据；实际成交链路必须实测 |
| P4：远程服务 | GM AdapterBundle、Server 配置、`gm-remote` 入口、远程数据与 tick 快照能力声明 | 外部策略经现有 Server 读数据和执行仿真订单；超时/断线/重复请求/跨账户/重启对账通过 |
| P5：集成与发布准备 | 可选依赖、安装指南、环境模板、doctor、示例、文档导航、回归结果 | 合入目标开发基线后重新验收；QMT/大 QMT/其他后端入口不受影响；冷启动及运行时版本指纹一致 |

P3 的真实成交受交易日限制。假期可以完成 SDK 只读检查和 fake SDK 的交易故障测试，不能据此宣布仿真撮合或实盘交易通过。部分成交无法稳定触发时，实测范围和回报重放范围分别标注。

P0–P2 可作为第一批实现，完成 Windows 本地标准接口；P3 验证真实仿真交易；再完成 P4–P5。实盘验收另设一次独立里程碑，不能由仿真通过自动推导。

## 配置与用户使用方式

已有 `GM_TOKEN`、`GM_STRATEGY_ID`、`GM_ACCOUNT_ID`、`GM_SERV_ADDR`、`GM_PYTHON_EXECUTABLE` 和数据超时配置。新增交易会话超时、请求日志路径、显式交易开关和账户模式校验。账户模式必须与实际账户身份校验共同生效，不能只凭一个 `simulation` 字符串判断可以下单。

实现完成后的目标入口如下，目前 `gm` Broker / Server 尚不可运行：

```text
Windows 本地：
  DEFAULT_DATA_PROVIDER=gm
  DEFAULT_BROKER=gm
  bullet-trade live strategy.py --broker gm

Windows 远程服务：
  bullet-trade server --server-type gm

外部执行器：
  选择 GM 远程数据源和 gm-remote Broker，使用同一套策略 API
```

数据行情和交易委托价格分别处理：研究用复权行情继续遵守数据合同；实际下单必须使用当前交易价格及最小报价单位，不能直接发送复权价格。LiveEngine 的交易价获取链路也纳入 P2/P3 验收。

SDK 留在匹配的 Windows 环境，非 Windows 策略机只安装普通 BulletTrade 与远程客户端。SDK 可选依赖懒加载；普通导入、CLI 帮助、其他后端的测试不要求安装 GM SDK。doctor 默认不交易、不撤单、不启动常驻服务。
